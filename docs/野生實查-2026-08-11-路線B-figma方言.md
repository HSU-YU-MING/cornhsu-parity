# 野生實查(路線 B):別人的 Figma 方言 × 官方實作

**日期**:2026-08-11。**動機**:FigmaDesignSource 與 Matcher 此前只吃過作者自己的
Figma 習慣。本輪用兩個公開設計系統的 community 檔(複製進帳號後以
`file_content:read` scope 的 token 讀取),對其官方網站/Storybook 跑 check——
測「別人畫的 Figma」:component/variant 結構、命名習慣、圖層組織。

**素材**:IBM Carbon v11(`qRzJ3fxF1g09NczsrugiXD`)、Ant Design Open Source
(`mXMoU5YGQr0P33RMoc1whS`)。原定第三組 Shopify Polaris 的 community 檔已 404(見 B5)。

## 三次實測

| # | 設計端 | 實作端 | 結果 |
|---|---|---|---|
| 1 | Carbon「Button」整頁變體表(2336 節點) | carbondesignsystem.com 的 Button 文件頁 | 配對 5/2336(0.2%),unmatched:no-anchor 2099、ambiguous 232;exit 1 |

## 發現

### B1【正面】FigmaDesignSource 消化野生檔零問題

COMPONENT_SET / COMPONENT / INSTANCE 節點型別、variant 語法命名
(`Type=primary, Shape=standard, …`)、巨型檔案(Carbon 87.2k 使用者的 kit)——
解析全數正常,無 crash、無型別噴錯。自家檔案從沒用過這些結構。

### B2【工作流真相,該寫進文件】變體總表不是可比對的 frame

設計系統 kit 的元件頁是「一張畫滿所有變體的表」,和任何真實頁面在結構上不相交——
實測 1 的 0.2% 配對率不是 bug,是誠實(Matcher 拒絕硬湊)。**路線 B 式的用法要選
「畫一個畫面」的 frame(screen-level),不是「畫所有變體」的 frame(sheet-level)**;
後者配 Storybook 的單一 story(實測 3)才是公平配對。這一段值得進 README 的
「怎麼挑 target.frame」指引。

### B3【可行動,候選規則】通用圖層名的 auto-name 假配對

實測 1 配到的 5 個節點裡,「Content」這個圖層名撞上文件站自己的 `#content` 容器,
產生 width 1969px vs 602px 等 critical 級荒謬落差。**通用名(Content/Header/Title/
Wrapper)在無關頁面上的名稱錨定,是傷害信任的假警報形狀**——對照 XamlContrast
「每條規則來自實查」:候選規則是 auto-name 配對加合理性檢查(例如箱體尺寸數量級
相符才接受,或通用名單字不做 auto-name)。列入 ROADMAP,動工前先蒐集更多樣本。

### B4【方言清單】自家樣本永遠長不出來的結構

空白字串當 frame 名(Ant Design 的三個頂層 frame 名稱是「 」)、分隔線式頁名
(`━ General ━━━`)、variant 語法名、元件內部的 wrapper/Icon/Vector 層。
Matcher 的名稱正規化(`NormalizeName`)對空白名回空字串 → 正確走 no-anchor,
沒有炸;但這些樣態該進測試資料庫。

### B5【生態事實】community 檔會消失

Shopify Polaris 的 community 檔(id 1293611962331823010)已 404。教訓:文件或
設定裡引用 community id 是會腐爛的;真正穩定的是**複製進自己帳號後的 file key**。

### B7【生態事實 → 已修訊息】免費方案的 API 額度是「天」級的,不是「分鐘」級的

補測第三組(Wikimedia Codex,`9rUskXS2M0CrpZgcfuYs34`,已複製並取得 file key)時
撞上 `429 Rate limit exceeded`,**`Retry-After: 367422` 秒 ≈ 4.3 天**——這是 Figma
方案級(免費方案)的 API 額度,連續掃十幾個 frame 就見底。兩個後果:

1. **`.parity/cache` 從「加速」升格為「命脈」**:額度內抓過的 frame 離線照用
   (本輪 Carbon/antd 的後續實測全靠 cache 跑完)。
2. **429 的錯誤訊息兩度進化**:原版誤導人查 scope/key;第一版修正說「等一分鐘」——
   對方案級額度仍是誤導;現在把 `Retry-After` 讀出來換算成分/時/天講給人聽。
   同一個 429,野外踩了兩層才把訊息修對。

Codex 的配對(Button 頁 vs doc.wikimedia.org 的 Codex demo)config 已備妥於實測
工作區,額度重置後即可執行(已於 2026-08-26 執行,見文末補測一節)。順帶:
Material 3 Design Kit(112 萬使用者的巨檔)在瀏覽器端複製時會讓分頁凍死,
不適合當實測素材。

### B6【正面,本輪最有價值的訊號】公平配對給出真實的還原度結論

實測 3:Figma kit 裡的按鈕文字節點 ↔ Storybook 渲染的 `<button>`,文字錨定配上,
**字級/字重/行高/字距/顏色全部 0 落差**——IBM 的設計 kit 與程式碼實作是真的一致,
Parity 用數字證實了這件事。這是「工具在野外能給出正確結論」的最強證據:
不一致時誠實列 unmatched(實測 1、2),一致時精確說一致(實測 3)。

## 補測(2026-08-26):第三組 Wikimedia Codex

B7 的額度重置後補跑。素材:Wikimedia Codex 的 community 檔(複製進帳號,
file key `9rUskXS2M0CrpZgcfuYs34`),對照實作端是 doc.wikimedia.org 的
Codex Button demo 頁。兩次實測,沿用 8/11 的兩種形狀:

| # | 設計端 | 實作端 | 結果 |
|---|---|---|---|
| 4 | Codex「Button」整頁變體總表(431 節點,1884×2177) | doc.wikimedia.org 的 Button demo 頁 | 配對 25/431(5.8%),unmatched:no-anchor 313、ambiguous 91、**size-implausible 2**;exit 1 |
| 5 | 單一變體 `Size=medium, Action=neutral, Weight=normal, State=default`(可見內容僅 Text 節點) | 同頁「Normal neutral」按鈕(mapFile 手動錨定) | **1/1 配對**;fontWeight/letterSpacing 全合,fontSize 14→16、color #202122→#404244 兩筆**真實分歧**;exit 1 |

### B8【規則回歸,正面+極限確認】B3 的尺寸防線首度野外回歸

8/11 提出的 B3 候選規則(auto-name 面積比 >16 拒配)已在 Matcher 落地
(`SizePlausible`)。這輪是規則上線後第一次吃到全新野生檔:

- **擋下 2 個假配對**(unmatched 原因 `size-implausible`)——規則在野外真的有效。
- 已知極限如預告:**auto-container(LCA 推論)不經過尺寸防線**,「Dark」圖層
  仍配到整個 `#app` 容器(高 1292 vs 10543px);同量級撞名(`Button` 圖層 ↔
  文件頁 `#button` 錨點,32px vs 23px)也照樣通過。假配對從 Carbon 那輪的
  「全部漏放」進步到「數量級荒謬的攔得住」,剩下的要語意才殺得掉(B3 原文結論不變)。

### B9【工作流真相】kit 佔位字讓文字錨定整組失效,mapFile 是設計好的逃生門

Codex kit 全部 129 個 Button 變體的文字一律是佔位字「Button text」,官網上
沒有任何按鈕用這個文字——救了實測 3(Carbon)的文字錨定在這種 kit 形狀上
**無從發動**。這不是誰的錯:kit 用佔位字是合理的設計習慣,但它意味著
「單一變體 vs 單一實作」的公平配對在 Codex 形狀上只剩 mapFile 一條路
(實測 5 用 3 行 map 完成 1/1 配對)。README 的「怎麼挑 target.frame」指引
(B2)該補這條:**kit 文字是佔位字時,直接上 mapFile,不用試文字錨定**。

另外兩個此輪才長出來的樣態:

- 該變體的 Icon 圖層在 kit 裡是 `visible:false`(元件名寫 icon + text,實際
  可見內容只有文字)——parser 正確跳過隱藏圖層,配對目標數 1 是誠實的。
- DX 小坑:`parity.config.json` 允許 `//` 註解,`parity.map.json` 不允許
  (讀取端沒開 comment handling),寫了會炸 JSON 解析錯。候選:兩邊行為對齊。

### B10【生態事實,B7 追記】額度是按回應成本計的,重置後照樣秒沒

額度重置後換新 token 實跑:僅 4 個 API 呼叫(其中一次是對整張總表的 depth=3
查詢)就再度 429,`Retry-After: 322070` 秒 ≈ 3.7 天。對照 8/11「連續掃十幾個
frame 見底」——**免費方案額度看起來按回應資料量/成本計,不是按次數**,
一張 2000+ 節點的總表查詢就能吃掉大半。因應:

- cache 命脈地位三度驗證:實測 4 成功前的那次 fetch 進了 cache,之後所有
  分析與實測 5 全程零 API。
- 可行 workaround(這輪實際用上):單一變體的 cache 檔可以**從已快取的大 frame
  離線合成**——抽出子樹、包回 `{"nodes":{"<id>":{"document":…}}}` 形狀存進
  `.parity/cache`,引擎照吃,公平配對零 API 跑完。
- 順帶:token 過期(Figma 個人 token 有 30/60/90 天效期)呈現為 403,現行
  錯誤訊息只提示查 scope/fileKey——候選改進:把「token 可能已過期」加進 403 hint。

### B11【本輪最有價值】公平配對抓到真的 kit-vs-實作分歧——與 B6 成對

實測 5 的兩筆落差經獨立驗證(瀏覽器 computed style 與 Parity 量測一致)是
**kit 與現行實作的真實分歧**,不是工具誤報:

- **color `#202122` → `#404244`**:kit 凍在 Codex 1.x 的 `color-base`(#202122,
  當年 #404244 是 `color-base--hover`);現行文件站的按鈕文字色已改走 #404244。
  community 檔複製進帳號後不會跟著上游改版——B5「community 檔會腐爛」的另一種形狀:
  檔案還在,**內容過期**。
- **fontSize `14` → `16`**:Codex 的兩種字級情境(MediaWiki 皮膚 14px base vs
  獨立文件站 16px)——kit 按 MediaWiki 情境畫,demo 站按獨立站渲染,兩邊都「對」,
  分歧真實存在。

與 B6 對照,兩個方向的結論都拿到了:Carbon 是「kit 與實作真的一致,工具用數字
說一致」;Codex 是「kit 與實作真的分歧,工具用數字指出分歧、且指出的每一筆都
查得到出處」。誠實列 unmatched(實測 1、2、4)、一致時說一致(實測 3)、
分歧時說分歧(實測 5)——三種形狀齊了。
